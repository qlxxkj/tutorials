# 第 16 课：版本发布与灰度策略

## 16.1 版本类型

| 版本 | 可见范围 | 用途 |
|------|---------|------|
| 开发版 | 开发者 + 体验成员 | 开发自测 |
| 体验版 | 体验成员（最多 92 人） | 内部测试 |
| 正式审核版 | 审核员 | 提审 |
| 线上版 | 所有用户 | 生产 |

## 16.2 发布流程

```
本地开发 → 上传开发版 → 设体验版 → 内部测试
                              ↓
                        提审（填版本号 + 备注）
                              ↓
                        审核通过 → 发布上线
```

**上传**：开发者工具 → 上传 → 填写版本号 + 备注 → 生成"开发版"

**体验版**：小程序后台 → 版本管理 → 开发版 → 设为体验版（体验成员扫码使用）

**提审**：版本管理 → 开发版 → 提交审核 → 填功能描述 + 测试账号 + 截图

**发布**：审核通过后 → 发布 → 全量上线

## 16.3 灰度发布（小程序专属）

微信支持按用户灰度发布，无需自建 A/B 测试框架：

1. 发布时选择"灰度发布"
2. 设置初始灰度比例（如 10%）
3. 在"版本管理"中逐步放量：10% → 30% → 50% → 100%

```
┌──────────────────────────────────────┐
│  版本 v1.2.0  灰度发布中             │
│  当前灰度：10%                       │
│  [扩大至 30%] [扩大至 50%] [全量]    │
└──────────────────────────────────────┘
```

> 灰度期间两个版本同时在线，用户随机命中。适合新功能的渐进验证。

## 16.4 回滚策略

```
发现严重 bug
    ↓
小程序后台 → 版本管理 → 将上一稳定版设为"发布"
    （新 bug 版立即下线，旧版恢复）
```

> 回滚是"重新发布旧版本"，不是 git revert，线上立即生效。

## 16.5 版本命名规范

```
主版本.次版本.修订号

v1.0.0  首次上线
v1.1.0  新功能（不破坏旧功能）
v1.1.1  bug 修复
v2.0.0  不兼容变更（数据结构、接口）
```

提交审核时备注写清楚本次版本主要变更，审核员会对照。

## 16.6 监控与告警

| 指标 | 工具 | 频率 |
|------|------|------|
| 云函数错误率 | 云开发控制台 → 日志 | 实时 |
| 接口成功率 | 自建打点 + 云函数统计 | 每小时 |
| 崩溃率 | 微信开发者工具 → 调试 → 错误上报 | 实时 |
| 用户反馈 | 小程序后台 → 用户反馈 | 每日 |

> 上线后 1 小时内重点盯云函数日志，灰度比例放大前先确认错误率正常。

---

**小结**：体验版是内部测试的关键节点；灰度发布让你控制风险；回滚是把旧版本重新发布，不是撤销。
